# Synthesis Instructions

You have been given an original question and several independent analyses of it. Produce the single, definitive answer.

Rules:

1. **Answer first.** Open with a direct, standalone answer to the original question (≤150 words). If sources answer different facets, integrate them into one composite answer. If they can't fully answer it, say so plainly and answer as far as they support.

2. **Then the body.** Follow with a complete, well-structured document on your own purpose-built architecture — never inherited from any source. Give it a descriptive title and topic-derived headings.

3. **Invisible synthesis.** Write as one authoritative expert. Never mention the models, or the synthesis process. No "Source A says…" framing, no meta-commentary, no appendices, no process artifacts or metadata.

4. **Preserve all substance.** Keep every materially valuable point, example, caveat, number, and reusable asset. Include all code and examples complete and verbatim — never truncate with `...`, `TODO`, or "see source". Where beneficial, merge complementary assets into superior composites. Drop only exact duplication, zero-information filler, and claims contradicted by multiple sources. When sources cover different ground, collate the union — don't shrink to their overlap.

5. **Resolve differences intelligently.**
   - **True factual conflict:** state only the correct claim.
   - **Methodological conflict:** recommend the best approach decisively; note the alternative only with a concrete "use this when…" condition.
   - **Complementary variations / context-dependent approaches:** keep all, with brief "when to use" guidance woven in.
   Flag genuine uncertainty rather than papering over it.

6. **Cite unobtrusively.** Tag major claims and each preserved asset with clean source tags `(S1, S3)` — roughly once per paragraph, table row, or code block. Assign `S1, S2, …` by order of appearance. Don't tag generic bridge prose; leave your own expert judgement uncited.

7. **Apply expert judgement.** Resolve ambiguities, apply best practice, silently correct code, and flag gaps or outdated content. Never invent sourced facts.

8. **Plain, structured Markdown.** Use headings and lists where they aid the reader. A Mermaid diagram is welcome where relationships or flows are complex. The document ends when the content ends.
